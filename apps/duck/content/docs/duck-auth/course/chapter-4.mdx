Until now the engine answered a script. This chapter puts it behind Express, where the session travels as a cookie and every response is built from the engine's intents.

## Learning goals

- Mount the sign-in, sign-out, session and provider routes.
- Write the routes that are yours: sign-up, verification, reset.
- Guard your own routes with the session and the CSRF check.
- Turn any thrown `AuthError` into a response with `errorToHttp`.

## One request

<MermaidDiagram chart={`sequenceDiagram
    participant B as Browser
    participant X as Express
    participant E as AuthEngine
    B->>X: POST /auth/signin with email and password
    X->>E: flows.signIn
    E-->>X: intents: set sid, set duck-csrf
    X-->>B: 200 with two Set-Cookie headers
    B->>X: POST /api/notes with cookies and x-csrf-token
    X->>E: CSRF check, resolveSession
    E-->>X: Ada's session
    X-->>B: 201`} />

The engine never touches Express's response. It answers **intents** (set this cookie, redirect there, send this JSON), and the Express adapter applies them.

<Step>The server</Step>

```ts title="src/server.ts"
import { orNull } from '@gentleduck/auth/core'
import {
  expressCsrf,
  mountProviderBegin,
  mountSession,
  mountSignIn,
  mountSignOut,
  toHeaders,
} from '@gentleduck/auth/server/express'
import { errorToHttp } from '@gentleduck/auth/server/generic'
import express, { type ErrorRequestHandler } from 'express'
import { auth } from './auth'

const notes = new Map<string, string[]>()

const app = express()
app.use(express.json())

app.post('/auth/signin', mountSignIn(auth))
app.post('/auth/signout', mountSignOut(auth))
app.get('/auth/session', mountSession(auth))
app.post('/auth/providers/:id/begin', mountProviderBegin(auth))

app.use(expressCsrf(auth))

app.post('/auth/signup', async (req, res) => {
  const { email, password } = req.body
  auth.passwords.assertStrength(password)
  const identity = await auth.identities.create({ profile: { email, username: email } })
  await auth.passwords.set(identity.id, password, auth.cfg.stores.credentials)
  await auth.flows.requestEmailVerification({ identityId: identity.id })
  res.status(201).json({ identityId: identity.id })
})

app.post('/auth/verify-email', async (req, res) => {
  await auth.flows.completeEmailVerification({ token: String(req.body.token) })
  res.status(204).end()
})

app.post('/auth/forgot-password', async (req, res) => {
  await auth.flows.requestPasswordReset({
    input: { email: String(req.body.email) },
    findIdentityByEmail: (email) => orNull(auth.identities.getByEmail(email)),
  })
  res.status(202).end()
})

app.post('/auth/reset-password', async (req, res) => {
  await auth.flows.completePasswordReset({ token: String(req.body.token), newPassword: String(req.body.password) })
  res.status(204).end()
})

app.use('/api', async (req, res, next) => {
  const resolved = await auth.resolveSession({ headers: toHeaders(req.headers) }).orNull()
  if (!resolved?.identity) return res.status(401).end()
  res.locals.session = resolved.session
  res.locals.identity = resolved.identity
  next()
})

app.get('/api/notes', (_req, res) => {
  res.json(notes.get(res.locals.identity.id) ?? [])
})

app.post('/api/notes', (req, res) => {
  const mine = notes.get(res.locals.identity.id) ?? []
  notes.set(res.locals.identity.id, [...mine, String(req.body.text)])
  res.status(201).json(mine.length + 1)
})

const onError: ErrorRequestHandler = (err, _req, res, _next) => {
  const { status, body } = errorToHttp(err)
  res.status(status).json(body)
}
app.use(onError)

app.listen(3000, () => console.log('DuckNotes on http://localhost:3000'))
```

<Step>Drive it with curl</Step>

```bash
npx tsx src/server.ts
```

In a second terminal, sign up, then verify with the token the server printed:

```bash
curl -s localhost:3000/auth/signup -H 'content-type: application/json' \
  -d '{"email":"ada@example.com","password":"correct-horse-battery"}'

curl -s localhost:3000/auth/verify-email -H 'content-type: application/json' \
  -d '{"token":"<token from the printed link>"}'
```

Sign in, keeping the cookies in `jar`, and write a note:

```bash
curl -s -c jar localhost:3000/auth/signin -H 'content-type: application/json' \
  -d '{"providerId":"password","input":{"email":"ada@example.com","password":"correct-horse-battery"}}'

curl -s -b jar localhost:3000/api/notes -H 'content-type: application/json' -d '{"text":"buy bread"}'
# {"ok":false,"error":{"code":"AUTH_CSRF","status":403}}

curl -s -b jar localhost:3000/api/notes -H 'content-type: application/json' \
  -H "x-csrf-token: $(awk '$6 == "duck-csrf" { print $7 }' jar)" -d '{"text":"buy bread"}'
# 1

curl -s -b jar localhost:3000/api/notes
# ["buy bread"]
```

Sign out, and the notes are closed again:

```bash
curl -s -b jar -c jar localhost:3000/auth/signout -X POST \
  -H "x-csrf-token: $(awk '$6 == "duck-csrf" { print $7 }' jar)"

curl -s -o /dev/null -w '%{http_code}\n' -b jar localhost:3000/api/notes
# 401
```

## What just happened

1. **The mounted handlers are duck-auth's own routes.** `mountSignIn` read the body, ran `flows.signIn` with the caller's IP and User-Agent and the sid the request came in with, and applied the intents as two `Set-Cookie` headers. They run their own CSRF check, which is why they sit above `expressCsrf`.
2. **Sign-up is yours.** What an account needs (a name, accepted terms, an invite) is your app's decision, so no adapter mounts a sign-up route. `assertStrength` refuses a weak password as `AUTH_INVALID_CREDENTIALS` without naming the rule.
3. **The first note was refused.** With a session cookie present, `expressCsrf` wants the `duck-csrf` cookie's value echoed in `x-csrf-token`. A page on another site can make the browser send the cookie, but cannot read it to echo. A request with no session gets only the origin checks, which is why sign-up and verification passed without a token.
4. **The guard is one middleware.** It resolves the session once and hands the session and identity on in `res.locals`. `.orNull()` makes a missing session a 401, while a store outage still reaches the error handler.
5. **Errors become responses in one place.** Every route throws, and `errorToHttp` maps an `AuthError` to its status and `{ ok: false, error: { code, status } }`. Anything else becomes a 500 that says nothing about the cause.

## Try it

1. Sign in with a wrong password. The answer is 401 `AUTH_INVALID_CREDENTIALS`, straight from `errorToHttp`.
2. Sign up with the password `short`. It is refused with the same code, and no account is created.
3. Run the reset: `POST /auth/forgot-password` with `{"email":"ada@example.com"}`, then `POST /auth/reset-password` with the printed token and a new `password`. The session in `jar` stops working.
4. Call `GET /auth/session` with the jar before and after signing out.
