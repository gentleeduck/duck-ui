The clients call the routes a [server adapter](/duck-auth/server) mounts: sign-in, sign-out, the session and a provider's begin. Every framework client wraps the vanilla one.

## What a call answers

No method throws. Each answers an envelope:

```ts
const res = await client.signIn({ providerId: 'password', input: { email, password } })

if (res.ok) showAccount(res.data.identity)
else if (res.error.code === 'AUTH_INVALID_CREDENTIALS') showError('Wrong email or password')
```

- Success is `{ ok: true, code, data }`. `signIn` answers the session the new cookie carries, as `getSession` does.
- Failure is `{ ok: false, error }`, the error as the server wrote it: its `code`, `status`, and any detail that code carries. Branch on the code; the [error reference](/duck-auth/core/errors) lists them.
- A request that never reached the server answers `AUTH_NETWORK_ERROR`; a server that answered something other than an envelope, `AUTH_HTTP_ERROR` with its status.

Dates come back as `Date`s. For a `/session` call made with your own `fetch`, `reviveSessionResult` does the same.

## Matching the server

- `baseUrl` is where the routes are mounted, `/auth` by default. Mounted at `/api/auth`, pass `baseUrl: '/api/auth'`.
- Requests send cookies, so a client on another origin needs the server to allow credentialed CORS from it.
- Every write sends the CSRF token from the companion cookie. That cookie is `__Host-duck-csrf` only when the session cookie is `Secure`, on `Path=/` and has no `Domain`; otherwise it is `duck-csrf`, as on http during development, and the client needs `csrfCookieName: 'duck-csrf'`. The transport's `csrfCookieName` answers which one it sets.
- The session is typed by your profile: `createAuthClient<Profile>()`, `useSession<Profile>()`.
