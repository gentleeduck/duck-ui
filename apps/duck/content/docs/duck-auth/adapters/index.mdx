An adapter is three stores: identities, credentials and sessions. Pass one as `stores`:

```ts
import { drizzlePgAdapter } from '@gentleduck/auth/adapters/drizzle/pg'

const auth = createAuth({
  baseUrl: 'https://app.example.com',
  stores: drizzlePgAdapter(process.env.DATABASE_URL ?? ''),
  // ...
})
```

| Adapter | Import | Holds | For |
| --- | --- | --- | --- |
| [Memory](/duck-auth/adapters/memory) | `adapters/memory` | All three, and orgs | Tests and local runs. `strict()` refuses it in production. |
| [Drizzle](/duck-auth/adapters/drizzle) | `adapters/drizzle/{pg,mysql,sqlite}` | All three | Production. |
| [Redis and Valkey](/duck-auth/adapters/redis) | `adapters/redis`, `adapters/valkey` | Sessions, events, nonces | Sessions across instances, and the shared state beside them. |

An [orgs store](/duck-auth/core/orgs#the-store) is yours to write over your own tables.

## Mixing stores

Each store is independent, so sessions can live in Redis beside identities in SQL:

```ts
import { session } from '@gentleduck/auth/adapters/redis'

const sql = drizzlePgAdapter(db)
createAuth({
  // ...
  stores: { identities: sql.identities, credentials: sql.credentials, sessions: session({ redis }) },
})
```

## Transactions

`auth.withTransaction(tx)` answers the engine bound to your transaction handle, so its writes commit or roll back with yours. Its events wait in `pending`, so flush them once the transaction commits:

```ts
await db.transaction(async (tx) => {
  const bound = auth.withTransaction(tx)
  const ada = await bound.identities.create({ profile: { email: 'ada@example.com', username: 'ada' } })
  await tx.insert(accounts).values({ ownerId: ada.id })
  return bound.pending
}).then((pending) => pending.flush())
```

Only a Drizzle adapter passed whole can join one. A hand-built mix and the memory adapter throw `AUTH_MISCONFIGURED`.

## Limiters

The limiter is what every sign-in, link request and challenge spends from. Pass one as `limiter`:

| Limiter | Import | Notes |
| --- | --- | --- |
| `redisLimiter({ redis })` | `limiters/redis` | Shared across instances. Default 10 per 15 minutes per key. |
| `valkeyLimiter({ redis })` | `limiters/valkey` | The same over an ioredis or iovalkey client. |
| `new MemoryLimiter()` | `limiters/memory` | One process only. |
| `noopLimiter()` | `limiters/mock` | Never refuses. Tests only. |

Without one, the engine counts in a `MemoryLimiter`. `strict()` refuses that in production, and the noop one: a limiter per process grants every budget once per instance.

## Writing your own

Implement `Identities.Store`, `Credential.Store` and `Sessions.Store` from `@gentleduck/auth/core`. The contract each method keeps is on its type.

- A missing row rejects with its not-found code, such as `AUTH_IDENTITY_NOT_FOUND`; it never answers `null`.
- A stale `expectedVersion` rejects with `AUTH_STALE_WRITE`, and a taken email, username or login with its own code.
- Extend `AdapterStore` from `@gentleduck/auth/adapters` and call through `run`: it maps what your driver throws onto the codes you declare, and anything else to `AUTH_ADAPTER_FAILED`.
- Give it a `withClient(tx)` answering the same stores on a transaction handle, and it can join `withTransaction`.
